# ТЗ: модуль стресс-тестирования Монте-Карло (mc\_stress)

Версия 1.0 · 21.10.2026 · Исполнитель: Senior Backend/Quantitative Programmer

## 0. Общие положения

**0.1 Цель.** Встроить в существующую систему бэктеста изолированный модуль `mc_stress`, который по результатам базового бэктеста оценивает устойчивость стратегии четырьмя методами: **A** (Монте-Карло по сделкам), **B** (тест «удача или навык»), **C** (синтетические ценовые ряды), **D** (робастность параметров). Выход: метрики риска, отчёты CSV/JSON/TXT, графики PNG, подробный лог.

**0.2 Вне области (v1).** Размер позиции (Kelly и т.п.), Heston/GARCH/jump-diffusion, MCMC, оптимизация портфеля, White's Reality Check/SPA. Архитектура должна позволять добавить их без правки ядра (абстракция `MCMethod`).

**0.3 Допущения о существующей системе.** Проверяются на этапе 0. При расхождении пишется адаптер, ядро системы не переписывается.

- Данные: один локальный файл (CSV/Parquet) со столбцами `timestamp, open, high, low, close[, volume]`.
- Конфиг: один файл YAML со стратегией (`strategy.params`) и параметрами симуляции (`data`, `backtest`).
- Бэктест — детерминированная чистая функция от (данные, параметры): без глобального состояния, без записи файлов и графиков внутри.
- Результат бэктеста содержит список сделок и кривую эквити.

**0.4 Стек.** Python ≥ 3.10; `numpy`, `pandas`, `scipy` (только `stats`, `stats.qmc`), `matplotlib` (бэкенд Agg), `PyYAML`, `psutil`, `pytest`. Numba, GPU и тяжёлые зависимости в v1 запрещены.

**0.5 Эталонный ПК (ограничение).** 2 физических ядра, 4 ГБ ОЗУ, без GPU. Все лимиты по умолчанию рассчитаны на него (раздел 9). Требование приоритетное: модуль **не имеет права** исчерпать память или заморозить систему.

**0.6 Обозначения.**

```
n_b      число баров;   n_t  число сделок;   N  число симуляций
E0       начальный капитал
r_j      доходность j-й сделки как доля эквити на момент входа, после комиссий, j=1..n_t
E_i[k]   эквити i-й симуляции после k-го шага (k=0..K)
T_years  длительность базового периода в годах = (t_last - t_first) / 365.25 суток
```

### 1.2 Правила изоляции

- Зависимость строго односторонняя: `mc_stress` → адаптер → стратегия. Базовая система импортирует из `mc_stress` только `run_monte_carlo` и вызывает её лишь при `monte_carlo.enabled: true`.
- Выходные файлы пишутся только в `results/mc_<UTC-время>_<hash8>/`. Каталоги базовой системы модуль не трогает.
- Исключение внутри `mc_stress` не должно ронять базовый бэктест: вызов обёрнут в try/except, результаты базового бэктеста сохраняются до запуска MC.
- Входные данные и конфиг не мутируются (массивы получают `flags.writeable = False`).

### 1.3 Контракты (`contracts.py`)

```python
@dataclass(frozen=True)
class Trade:
    entry_idx: int          # индекс бара входа в массиве свечей
    exit_idx: int
    side: int               # +1 лонг, -1 шорт
    ret: float              # доля эквити, после комиссий и проскальзывания
    cost: float | None      # суммарные издержки сделки в долях (если известны)

@dataclass
class BacktestResult:
    trades: list[Trade]
    equity: np.ndarray      # float64, длина n_b+1, equity[0] = E0
    index: pd.DatetimeIndex
    initial_capital: float
    params: dict
    runtime_sec: float

class StrategyAdapter(Protocol):
    def run(self, ohlcv: pd.DataFrame, params: dict) -> BacktestResult: ...
    def param_space(self) -> dict[str, ParamSpec]: ...   # name -> (type, low, high)

class MCMethod(ABC):
    name: str
    def estimate_cost(self, ctx) -> CostEstimate: ...     # время и память до запуска
    def run(self, ctx, n_sims: int, rng_streams) -> MethodResult: ...
```

Адаптер обязан быть чистым и детерминированным: два вызова с одинаковыми аргументами дают идентичный результат (проверяется на этапе S2).

### 1.4 Режимы вызова

- **Hook (в процессе):** `run_monte_carlo(cfg, ohlcv, base_result, adapter)` вызывается из `main.py` сразу после базового бэктеста. Базовый результат берётся из памяти.
- **CLI (после):** `python -m mc_stress --config config.yaml [--methods A,B] [--dry-run] [--resume RUN_DIR]`. Модуль сам один раз запускает адаптер для базового результата. `--dry-run` выполняет только S0–S3 и печатает оценку времени и памяти.

Методам A и B1 нужны только сделки и свечи. Методам B2, C, D нужен адаптер (повторные прогоны стратегии).

### 1.5 Взаимодействие с конфигом и данными

- Из конфига читаются: `data.path`, `data.timeframe`, `strategy.params`, `strategy.param_ranges` (для D), `backtest.initial_capital`, секция `monte_carlo`. Для данных используется загрузчик самой системы, второй не пишется.
- Файл конфига и файл данных только читаются. В run-каталог пишутся `config_resolved.yaml` (с подставленными значениями по умолчанию) и SHA-256 обоих файлов (для воспроизводимости).
- Неизвестные ключи в `monte_carlo` — ошибка (код выхода 2).

## 4. Математический аппарат

### 4.0 Общая модель и генератор случайности

```
fixed_fraction:  E[k] = E[k-1] * (1 + r_k)    =>  log E[k] = log E0 + sum_{j<=k} log1p(r_j)
additive:        E[k] = E[k-1] + E0 * r_k
r_k клипуется снизу значением -0.999999 (эквити не уходит в 0 или минус)
Ось: для A и B1 — номер сделки (K = n_t); для B2, C, D — бар (K = n_b).
CAGR_i = (E_i[K] / E0)^(1/T_years) - 1;  при E_i[K] <= 0:  CAGR_i = -1
T_years берётся из базового периода и одинаково для всех симуляций.
```

Генератор: `np.random.Generator(PCG64)`. Из `SeedSequence(seed)` порождаются независимые потоки по ключу (метод, номер чанка). Результат не зависит от `n_jobs` и размера чанка.

### 4.1 Метод A — Монте-Карло по сделкам

**Вход:** вектор `r = (r_1..r_n)`, `n = n_t`. Каждая симуляция строит индексы `I = (I_1..I_n)` и последовательность `r'_j = r[I_j]`.

**Сценарии (каждый — отдельный независимый прогон на N симуляций):**

- **shuffle:** `I = π`, π равномерна на S\_n. Инвариант: мультипликативная итоговая эквити не меняется, меняется только путь (просадка).
- **bootstrap:** `I_j ~ iid Uniform{0..n-1}`. Меняется и итог.
- **stationary** (Politis–Romano): `p = 1/b`. `I_1 ~ U`. Для j ≥ 2: с вероятностью p `I_j ~ U` (новый блок), иначе `I_j = (I_{j-1}+1) mod n`. Длина блока геометрическая со средним b. Сохраняет серийную зависимость (серии убытков). `b = auto` → `max(2, round(n^(1/3)))`.
- **skip (опция):** `M_j ~ Bernoulli(1 - skip_prob)`, `r''_j = M_j * r'_j`.
- **cost\_stress (опция):** `r'''_j = r''_j - c_j`, `c_j = median * exp(sigma * Z_j)`, `Z_j ~ N(0,1)`, применяется только к ненулевым (не пропущенным) сделкам.

Векторизация stationary (обязательна, циклов по симуляциям нет):

```python
p = 1.0 / b
new = rng.random((N, n)) < p;  new[:, 0] = True
starts = rng.integers(0, n, size=(N, n))
pos = np.maximum.accumulate(np.where(new, np.arange(n), 0), axis=1)
base = np.take_along_axis(starts, pos, axis=1)
idx = (base + (np.arange(n) - pos)) % n
ret = r[idx].astype(np.float32)
logE = np.cumsum(np.log1p(np.maximum(ret, -0.999999)), axis=1)   # для fixed_fraction
```

**Заголовочные метрики** берутся из сценария `primary`. Остальные сценарии попадают в отчёт как сравнение.

### 4.2 Метод B — тест «удача или навык»

**Нулевая гипотеза H0:** стратегия не имеет предсказательной силы; результат объясним случайным совпадением позиций с рынком.

**Статистика T** (конфиг `B.statistic`):

```
total_log_return:  T = sum_j log(1 + r_j)
profit_factor:     T = sum(r_j | r_j>0) / |sum(r_j | r_j<0)|
sharpe_trade:      T = mean(r) / std(r, ddof=1) * sqrt(n)
```

**p-value (общая формула, односторонний тест):**

```
p = (1 + #{k : T_k >= T_obs}) / (1 + N)
```

Минимально достижимое p равно 1/(1+N). Поправка на перебор: `p_adj = min(1, p * strategies_tried)` (Бонферрони), при `strategies_tried > 1` пишется WARNING, что поправка консервативна.

**B1 — случайный сдвиг расписания сделок (без перезапуска стратегии, дёшево).** Для каждой сделки известны `side_i`, длительность `h_i = exit_idx - entry_idx`. Выбирается один общий циклический сдвиг `tau ~ U{tau_min .. n_b - tau_min}`, `tau_min = max(h_max, ceil(0.05 * n_b))`. Новые входы: `entry'_i = (entry_i + tau) mod n_b`. Сохраняются стороны, длительности, перекрытия и интервалы между сделками, нарушается только связь с ценой. Доходность сделки:

```
L[k] = ln(C[k]/C[0])  (кумулятивный лог-ряд закрытий)
r'_i = side_i * (exp(L[t+h_i] - L[t]) - 1) - cost_i,   t = entry'_i
если t+h_i >= n_b: пересечение границы — возврат на границе (L[n_b-1]-L[t]) + (L[t+h_i-n_b]-L[0]), скачок между последним и первым баром пропускается
cost_i = Trade.cost, если известно, иначе средние издержки на сделку из базы
```

Альтернатива `b1_mode: uniform`: независимые равномерные входы (допустима только если база разрешает перекрытия позиций).

**B2 — перестановка блоков доходностей баров (с перезапуском стратегии).** Из свечей строятся признаки (4.3), строки делятся на блоки длины `b_perm` (по умолчанию 20; не меньше максимального периода индикатора стратегии), блоки перемешиваются без возвращения (неполный хвостовой блок остаётся на месте), цена собирается заново от `C_0`. Стратегия запускается на каждой перестановке, считается `T_k`. Тест отвечает на вопрос: использует ли стратегия временную структуру, которая разрушается при перемешивании.

**Интерпретация (пороги конфигурируемы):** `p < 0.05` — PASS; `0.05 ≤ p < 0.20` — WEAK; `p ≥ 0.20` — FAIL. Вердикт выдаётся отдельно для B1 и B2.

### 4.3 Метод C — синтетические ценовые ряды

**Признаки бара (для t = 1..n\_b-1):**

```
g_t = ln(O_t / C_{t-1})      гэп
u_t = ln(H_t / max(O_t,C_t)) верхняя тень (>= 0)
d_t = ln(min(O_t,C_t) / L_t) нижняя тень (>= 0)
c_t = ln(C_t / O_t)          тело
v_t = V_t (если есть)
вектор бара: f_t = (g_t, c_t, u_t, d_t, v_t)
```

**C1 (по умолчанию) — стационарный блочный бутстрэп строк `f_t`.** Индексы строятся по формуле 4.1 (stationary) на пространстве `{1..n_b-1}` с `b = auto`. Целые векторы бара переставляются вместе, поэтому сохраняются связи внутри бара, форма распределения, кластеризация волатильности внутри блока. Цена собирается:

```
C'_0 = C_0
O'_t = C'_{t-1} * exp(g'_t);   C'_t = O'_t * exp(c'_t)
H'_t = max(O'_t, C'_t) * exp(u'_t);   L'_t = min(O'_t, C'_t) * exp(-d'_t)
```

**Нейтрализация дрейфа** (`drift`): `m_hat = mean(g_t + c_t)` — средний лог-доход за бар на исходных данных; `m_star = 0` (zero), `m_hat` (none) или `annual/bars_per_year` (value). Смещение `delta = m_hat - m_star` вычитается из `c'_t` после сэмплирования (`c'_t -= delta`). `drift: zero` — режим по умолчанию: стратегия не должна «жить» на историческом росте актива. После смещения `H'`, `L'` пересчитываются так, чтобы сохранялось `L' ≤ min(O',C') ≤ max(O',C') ≤ H'`.

**`session_aware: true`:** блок может начинаться только на баре с тем же временем суток, что и бар, который он замещает (для стратегий с торговыми сессиями). Временная ось (`timestamp`) синтетики совпадает с реальной.

**C2 — параметрическая модель (`gbm_t`, только для стратегий по закрытию и OHLC).**

```
sigma_hat = std(x_t),  x_t = ln(C_t/C_{t-1}),  оценка по всему окну данных
Z ~ Student-t(nu=t_dof), нормированная до единичной дисперсии:  Z_s = Z * sqrt((nu-2)/nu)
x'_t = m_star + sigma_hat * Z_s
O'_t = C'_{t-1};  C'_t = C'_{t-1} * exp(x'_t)
тени: u'_t, d'_t сэмплируются iid из эмпирических u, d
```

**Запуск:** стратегия запускается на каждом синтетическом ряду, ряды генерируются по одному (память O(n\_b)). Для каждого ряда сохраняются скалярные метрики и, при попадании в резервуар (`keep_curves`), кривая эквити.

### 4.4 Метод D — робастность параметров

**Пространство.** Из `strategy.param_ranges` берутся параметры `θ = (θ_1..θ_k)` с типами `float|int|categorical` и границами `[low_k, high_k]`. Базовая точка — `strategy.params`.

**Сэмплирование.** M = `n_points`. Равномерное покрытие через `scipy.stats.qmc.LatinHypercube(d=k, seed=rng)`. Точка:

```
theta'_k = clip( theta_k * (1 - radius + 2*radius*u_k),  low_k, high_k ),  u_k in [0,1] из LHS
int-параметры округляются; дубликаты удаляются (число уникальных точек пишется в лог)
categorical-параметры не возмущаются
```

**Шум данных (опция, `data_noise_kappa > 0`).** Для каждого прогона независимо: `sigma_bar = std(ln(C_t/C_{t-1}))`, `xi_t ~ N(0, (kappa * sigma_bar)^2)`, все четыре цены бара умножаются на `exp(xi_t)`. Порядок OHLC сохраняется, между барами возникает дополнительный шум гэпов. Это проверка чувствительности к микроструктурным отклонениям данных.

**Целевая метрика** `J` (по умолчанию `sharpe_ann` — годовой Шарп по эквити баров; допустимы `car`, `calmar`, `final_log_return`). Запускается адаптер для M точек и базовой точки `J_0`.

**Метрики робастности:**

```
plateau_ratio = (1/M) * sum 1{ J_m >= 0.5 * J_0 }     (требует J_0 > 0)
p_positive    = (1/M) * sum 1{ J_m > 0 }
CV            = std(J) / |mean(J)|
peak_z        = (J_0 - median(J)) / (IQR(J) / 1.349)
```

`peak_z > 2` означает, что базовая точка — изолированный пик (признак переобучения), выдаётся флаг `ISOLATED_PEAK`.

**Вердикт (пороги конфигурируемы):** PASS при `plateau_ratio ≥ 0.6` и `p_positive ≥ 0.8` и `peak_z ≤ 2`; FAIL при `plateau_ratio < 0.3` или `p_positive < 0.5`; иначе WEAK.

**`oat_sweep: true` (опция):** для каждого параметра отдельно по 9 точек на `[θ(1-radius), θ(1+radius)]` при прочих неизменных. Стоит `9*k` прогонов, включать осознанно. Результат — линии чувствительности для графика (раздел 8).

## 5. Метрики риска и статистика

Все формулы реализуются в `metrics.py` как чистые функции над `numpy`-массивами. Скалярные метрики считаются в float64 (суммы логарифмов через float64-аккумулятор), кривые хранятся в float32.

### 5.1 Метрики по набору из N кривых

```
MDD_i         = max_k ( 1 - E_i[k] / max_{j<=k} E_i[j] )            # доля, >= 0
Expected MDD  = (1/N) * sum_i MDD_i;   MDD_q05, MDD_q50, MDD_q95 — выборочные квантили
Final_i       = E_i[K] / E0
Median Equity = median_i E_i[K];   медианная кривая = поточечная медиана по k
CAGR_i        = Final_i ^ (1/T_years) - 1          (см. 4.0)
CAR25         = quantile_0.25 ( CAGR_i )           (numpy, method=linear)
Ruin_floor_i  = 1{ min_k E_i[k] <= equity_floor * E0 }
Ruin_dd_i     = 1{ MDD_i >= max_dd_limit }
Probability of Ruin:  PoR = (1/N) * sum_i Ruin_i      (считать оба варианта, floor и dd)
SE(PoR) = sqrt( p*(1-p)/N );   p = PoR, z = 1.96
Wilson 95%:  centre = (p + z^2/(2N)) / (1 + z^2/N)
             half   = z * sqrt( p*(1-p)/N + z^2/(4*N^2) ) / (1 + z^2/N)
Если PoR = 0: сообщать верхнюю границу 3/N (правило трёх), а не нулевую вероятность
P_profit      = (1/N) * sum_i 1{ Final_i > 1 }
CVaR5(Final)  = mean( Final_i | Final_i <= q_0.05(Final) )
Доверительные интервалы 5% / 50% / 95%:  [q_0.05(X), q_0.50(X), q_0.95(X)]
для X из {Final, CAGR, MDD}; для метода D — для J
```

Примечание для сценария `shuffle` метода A: `Final`, `CAGR`, `Median Equity` совпадают с базой по построению (4.1); в отчёт они выводятся с пометкой `invariant`, содержательны только MDD и PoR.

### 5.2 Сравнение с базовым бэктестом

```
rank_base(X)       = (1/N) * sum_i 1{ X_i <= X_base }     # перцентиль базы в распределении MC
bias_mean          = mean_i( ln Final_i ) - ln Final_base  # смещение математического ожидания
degradation_CAGR   = 1 - Q50(CAGR) / CAGR_base              (если CAGR_base > 0)
CAR25_ratio        = CAR25 / CAGR_base
MDD_ratio          = MDD_q95 / MDD_base
RecoveryRatio      = Median Equity / Final_base
```

Высокий `rank_base(Final)` (например, > 0.9) означает, что исторический путь был заметно удачнее типичного: сигнал переоценки результата бэктеста.

### 5.3 Вердикты (секция `monte_carlo.verdict`, пороги по умолчанию)

| Метод | PASS | FAIL |
| --- | --- | --- |
| A | PoR ≤ 0.05, CAR25 > 0, MDD\_q95 ≤ max\_dd\_limit | PoR > 0.20 или P\_profit < 0.5 |
| B (B1 и B2) | p\_adj < 0.05 | p\_adj ≥ 0.20 |
| C | P\_profit ≥ 0.70, CAR25 > 0 | P\_profit < 0.50 |
| D | см. 4.4 | см. 4.4 |

Между PASS и FAIL — WEAK. Общий вердикт — худший из вердиктов выполненных методов. Любой флаг `LOOKAHEAD_SUSPECTED` (раздел 10, AT-12) делает вердикты недействительными (`INVALID`).

## 6. Логирование

**Файлы.** `run.log` — текст для человека, формат `ГГГГ-ММ-ДД ЧЧ:ММ:СС.мммZ | LEVEL | STAGE | message` (UTC). `run.jsonl` — по одному JSON-событию на строку для машинного разбора; ротация при 50 МБ. Все ошибки дублируются с traceback. Лог пишется построчно с flush, чтобы при аварии файл оставался полным.

| Событие | Обязательные поля |
| --- | --- |
| RUN\_START | run\_id, utc, версии python/numpy/pandas/scipy, платформа, число ядер, RAM всего/доступно, sha256 конфига и данных, master\_seed, профиль, методы |

| METHOD\_START / METHOD\_END | метод, сценарий, N, длительность, число отброшенных симуляций |
| CHUNK | метод, сценарий, номер чанка, число выполненных симуляций, число итераций, elapsed, ETA, RSS МБ, spawn\_key генератора, число NaN |
| ANOMALY | code, метод, сценарий, spawn\_key (достаточный для воспроизведения), описание |

**Детализация по симуляциям.** На уровне INFO пишется только событие CHUNK (иначе лог раздувается). Уровень DEBUG (`--log-level DEBUG`) пишет строку на каждую симуляцию: spawn\_key, число сделок, Final, MDD, число итераций. Для симуляций с аномалией строка пишется всегда. Любую симуляцию можно воспроизвести отдельно: `python -m mc_stress --config config.yaml --replay A:stationary:3:17` (метод:сценарий:чанк:симуляция).

**Коды выхода.** 0 — OK; 1 — непредвиденная ошибка; 2 — ошибка конфига; 3 — ошибка данных; 4 — недостаточно сделок; 5 — ошибка базового результата или адаптера (детерминизм, реконсиляция); 6 — прерывание по ресурсам без результата; 7 — частичный результат (остановка пользователем или по времени, итоги сохранены).

## 9. Ресурсы и оптимизация (ограниченный ПК)

**Принцип:** до любых вычислений модуль оценивает стоимость и сам укладывается в бюджет. Пользователь не должен получить зависший ПК.

### 9.1 Профили и потолки

| Параметр | lite (по умолчанию) | standard | heavy |
| --- | --- | --- | --- |
| Потолок N: A, B1 | 2000 | 10000 | 50000 |
| Потолок N: B2 | 200 | 500 | 2000 |
| Потолок N: C | 100 | 300 | 1000 |
| Потолок точек D | 60 | 150 | 500 |
| max\_ram\_mb | 1500 | 2500 | 4000 |
| max\_runtime\_min | 10 | 30 | 120 |
| keep\_curves | 100 | 200 | 300 |

Эффективное N = min(значение из конфига, потолок профиля, результат preflight). Профиль `heavy` без `allow_heavy: true` отклоняется (код 2, `HEAVY_BLOCKED`). Значения в примере конфига (раздел 2) укладываются в потолки lite.

### 9.2 Preflight (S3)

1. **Память.** Для векторных методов (A, B1): `mem_chunk = N_chunk * K * 4 Б * 3` (индексы int32, доходности float32, логарифм эквити float32). Размер чанка `N_chunk = max(1, floor(0.4 * max_ram_bytes / (K * 4 * 3)))`. Матрица всех кривых `N * (K+1) * 4 Б`: если больше `0.3 * max_ram_bytes`, она пишется в `np.memmap` в run-каталоге, а поточечные квантили считаются блоками по 1024 столбца.
2. **Время.** Калибровка: 30 симуляций векторных методов и замер `runtime_sec` базового прогона. `t_est = sum_m ( N_m * t_one_m ) * 1.1 / n_jobs_eff`. Для B2, C, D `t_one = runtime_sec` адаптера плюс время генерации ряда.
3. **Автоуменьшение.** Если `t_est > 0.8 * max_runtime`, уменьшаются N дорогих методов (B2, C, D) пропорционально до укладки в бюджет. Нижние границы: B2 ≥ 99 (разрешение p-value 0.01), C ≥ 30, D ≥ 20, A и B1 ≥ 200. Если и минимумы не помещаются — метод пропускается (`METHOD_SKIPPED_RESOURCES`), остальные выполняются. В отчёте помечается `downscaled: true`, эффективное N и предупреждение о более широких интервалах.
4. `--dry-run` печатает этот план и выходит. `--smoke` ставит N=20 для всех методов (проверка pipeline за секунды).

### 9.3 Исполнение

- Порядок методов от дешёвых к дорогим: A, B1, D, C, B2. Первый запуск на слабом ПК рекомендуется ограничить `methods: [A, B]` с B2 выключенным.
- Методы A и B1 — полностью векторные, без python-циклов по симуляциям. B2, C, D — цикл по симуляциям (адаптер вызывается N раз); данные передаются как numpy-представления без копирования DataFrame.
- `n_jobs = 1` по умолчанию. Максимум `min(n_jobs, физические_ядра - 1)`; при `n_jobs > 1` используется `multiprocessing` со стартом `spawn`, входные массивы раздаются через `shared_memory` (только чтение), бюджет RAM делится на число процессов, приоритет воркеров понижен (`os.nice(10)` / `BELOW_NORMAL_PRIORITY_CLASS`), чтобы ПК оставался отзывчивым. Результат не зависит от `n_jobs` (4.0).
- **Сторожа** (проверка после каждого чанка и каждые 10 симуляций): RSS процесса > 0.9 · `max_ram_mb` или доступная память системы < 500 МБ; затраченное время > `max_runtime_min`; файл `<run_dir>/STOP` либо SIGINT. Реакция: корректная остановка после текущей симуляции, сохранение частичных результатов, `partial: true`, код 7. Исключение `MemoryError` не должно доходить до пользователя.
- **Чекпоинты:** после каждого чанка скалярные метрики пишутся в `checkpoints/`; `--resume RUN_DIR` продолжает прогон, итог идентичен непрерывному.
- График и отчёт не требуют полной матрицы кривых в памяти (блочные квантили, резервуар кривых).

**Дополнение к конфигу (раздел 2):** необязательный ключ `monte_carlo.fit_end: null` — последний timestamp окна, по которому оцениваются параметры генераторов (sigma, m\_hat, эмпирические признаки C/B2). Значение `null` означает весь ряд; тогда оценка in-sample, и в отчёт пишется флаг `IN_SAMPLE_FIT`.

## 10. Критерии приёмки

Все тесты — автоматические (`pytest`), запускаются командой `pytest mc_stress/tests -q`. Приёмка требует прохождения всех пунктов.

| ID | Проверка | Критерий |
| --- | --- | --- |
| AT-01 | Воспроизводимость: два запуска с seed=1; `n_jobs=1` и `n_jobs=2` | `summary.json` и `sims_*.csv.gz` совпадают побайтно (кроме utc и runtime) |
| AT-02 | Инвариант shuffle (fixed\_fraction) | max abs(Final\_i − Final\_base) / Final\_base ≤ 1e-9; мультимножество r не изменилось |
| AT-03 | Bootstrap: несмещённость | при N=20000 среднее средних доходностей отличается от mean(r) не более чем на 4·s/√(n·N) |
| AT-04 | Stationary bootstrap | средняя длина блока в выборке = b ± 5%; доля пар I\_{j+1} = I\_j + 1 равна 1 − 1/b ± 0.02 |
| AT-05 | skip и cost\_stress | доля пропусков = skip\_prob ± 3σ биномиального; медиана extra cost = median ± 5% |
| AT-06 | Корректность метрик | на наборе кривых с известными ответами MDD, CAGR, CAR25, PoR, Wilson совпадают с ручным/numpy расчётом (atol 1e-12); PoR симметричного блуждания ±1 (additive, n=100, барьер −10) при N=50000 отличается от точного динамического программирования не более чем на 3·SE |
| AT-07 | p-value под H0 | стратегия = случайные сигналы на случайном блуждании; 300 повторов B1 (N=199): доля p<0.05 в \[0.02; 0.09\]; KS-тест равномерности p-value > 0.01 |
| AT-08 | Мощность B | стратегия с заложенным edge (тестовый сигнал: знак следующей доходности с шумом): p<0.01 не менее чем в 95% повторов |
| AT-09 | Валидность OHLC синтетики | на ≥ 1000 рядов C1 и C2: 100% баров удовлетворяют L ≤ min(O,C) ≤ max(O,C) ≤ H, цены > 0, нет NaN/inf |

## 11. Порядок работ и поставка

1. **Этап 0.** Аудит интеграции: написать адаптер, подтвердить допущения 0.3, пройти проверки S2 (детерминизм, реконсиляция). Открытые вопросы, которые исполнитель обязан закрыть до кода: определение `ret` сделки (доля эквити, учёт комиссий), режим `equity_mode` базы, наличие поля `cost`, допускаются ли перекрывающиеся позиции.
2. **Этап 1.** Ядро: `config`, `rng`, `data_validation`, `metrics`, `logging_setup`, `resources`.
3. **Этап 2.** Методы A и B1, отчёты, графики G1–G4 (самое дешёвое и самое полезное; после этого этапа модуль уже применим).
4. **Этап 3.** Методы D, C, B2 с автоуменьшением и сторожами.
5. **Этап 4.** Приёмка AT-01…AT-21.

**Поставка:** код пакета, тесты, `README.md` (запуск, описание ключей, примеры), `config.example.yaml`, `requirements.txt` с закреплёнными версиями, пример полного прогона на тестовых данных (папка результатов).

**Ограничение интерпретации (зафиксировать в README).** Монте-Карло не лечит переобучение: он показывает устойчивость результата при заданной модели случайности. Метод не заменяет out-of-sample и walk-forward проверку, а результаты не являются гарантией будущей доходности.
